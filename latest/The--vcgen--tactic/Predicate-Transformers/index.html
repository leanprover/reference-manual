17.2. Predicate Transformers🔗

A predicate transformer semantics is an interpretation of programs as functions from predicates to predicates, rather than values to values. A postcondition is an assertion that holds after running a program, while a precondition is an assertion that must hold prior to running the program in order for the postcondition to be guaranteed to hold.

The predicate transformer semantics used by vcgen transforms postconditions into the weakest preconditions under which the program will ensure the postcondition. An assertion P is weaker than P' if, in all states, P' suffices to prove P, but P does not suffice to prove P'. Logically equivalent assertions are considered to be equal.

The predicates in question can be stateful: they can mention the program's current state. Furthermore, postconditions can relate the return value and any exceptions thrown by the program to the final state. Each program type that can be used with vcgen is assigned an assertion type and an exception postcondition type by an instance of WP. For a state monad such as StateM Nat, an assertion is a predicate on the state, of type Nat → Prop. A postcondition additionally takes the return value as its first argument, and the exception postcondition includes an assertion for each exception that the program can throw.

17.2.1. Assertion Lattices🔗

The predicate transformer semantics of programs is based on a logic in which propositions may mention the program's state. Here, “state” refers not only to mutable state, but also to read-only values such as those that are provided via ReaderT. Different program types have different assertion types, which can be any complete lattice. More specifically, assertion types instantiate Assertion, which is a Lean.Parser.Command.classAbbrev : commandExpands ``` class abbrev C <params> := D_1, ..., D_n ``` into ``` class C <params> extends D_1, ..., D_n attribute [instance] C.mk ``` class abbrev over CompleteLattice that is recognized by vcgen.

The lattice structure provides the logical vocabulary of assertions:

  • The order relation ⊑ is entailment.

  • The meet ⊓ is conjunction and the join ⊔ is disjunction.

  • The top element ⊤ is the trivial assertion and the bottom element ⊥ is the absurd assertion.

  • The indexed supremum ⨆ is existential quantification and the indexed infimum ⨅ is universal quantification. Their notation resembles that of ordinary quantifiers; for example, ⨆ x : α, P x asserts the existence of something that satisfies P.

  • The Heyting implication ⇨ is implication internal to the assertion language.

The difference between entailment and implication is that entailment is a statement in Lean's logic, while implication is internal to the assertion language: for assertions P and Q, P ⊑ Q is a Prop while P ⇨ Q is again an assertion.

Std.WP comes with Assertion instances for Prop, Unit, function types, and pairs. The lattice operations on Prop coincide with the ordinary logical connectives, with entailment being implication. The lattice operations on a function type such as Nat → Prop operate pointwise, so entailment of state predicates is universally-quantified implication. The lattice operations on a pair such as (Nat → Prop) × (Bool → Prop) operate component-wise, so entailment of paired predicates is the conjunction of entailments of the component predicates.

Entailment at Different Assertion Types

At Prop, entailment is implication:

example (P Q : Prop) : (P ⊑ Q) = (P → Q) := rfl

At a state predicate type, entailment is implication at every state:

example (f g : Nat → Prop) : (f ⊑ g) = ∀ n, f n → g n := rfl

Entailment of pairs is conjunction of entailments:

example (f₁ f₂ : Nat → Prop) (g₁ g₂ : Bool → Prop) : ((f₁, g₁) ⊑ (f₂, g₂)) = ((f₁ ⊑ f₂) ∧ (g₁ ⊑ g₂)) := rfl

A concrete entailment between state predicates can be proved by unfolding the entailment order and reasoning about each state:

def Positive : Nat → Prop := fun n => 0 < n def AtLeastTwo : Nat → Prop := fun n => 2 ≤ n example : AtLeastTwo ⊑ Positive := ⊢ AtLeastTwo ⊑ Positive ⊢ ∀ (x : Nat), 2 ≤ x → 0 < x x:Nath:2 ≤ x⊢ 0 < x All goals completed! 🐙

An assertion of the form ⌜p⌝ is pure: its truth is independent of the state. At the assertion type Prop, ⌜p⌝ is the proposition p itself, and at a state predicate type such as Nat → Prop, it is the constant predicate fun _ => p. Specifications for a concrete monad can therefore state propositions directly, as in fun s => s = n. Corner brackets are necessary when the assertion type is abstract, as in a specification that quantifies over a monad and its assertion type Pred. In this case, a proposition such as n = k is not an assertion, but ⌜n = k⌝ embeds it into Pred. The monad-polymorphic example at the end of this chapter uses corner brackets for this reason. vcgen moves pure preconditions into the ordinary Lean context, where they become hypotheses of the verification conditions.

Assertions for State Monads

The predicate ItIsSecret expresses that a state of type String is "secret":

def ItIsSecret : String → Prop := fun s => s = "secret"

Entailment between such assertions is pointwise implication:

example : ItIsSecret ⊑ (⌜True⌝ : String → Prop) := ⊢ ItIsSecret ⊑ ⌜True⌝ All goals completed! 🐙

17.2.2. Exception Postconditions🔗

A postcondition for successful termination is a function from the return value to an assertion. Programs that can throw exceptions additionally require an exception postcondition that asserts what holds when the program throws an exception. The exception postcondition type of a given monad is determined by its WP instance.

For example, the WP instance for ExceptT String (StateM Nat) Bool determines Nat → Prop as the assertion type, hence Bool → Nat → Prop as the postcondition type, and String → Nat → Prop as the exception postcondition type. A monad without exceptions has the exception postcondition type Unit.

For a base monad with assertion type Pred and exception postcondition type EPred, an exception layer such as ExceptT ε contributes one more exception postcondition, which gives the type (ε → Pred) × EPred.

Since unit and pair types come with Assertion instances, these “stacks” of exception postconditions are automatically assertions as well. The WP instances for monad transformers ensure that stacks of monad transformers have corresponding exception postcondition stacks.

syntaxException Postcondition Stacks

The notation EStack⟨e₁, e₂, ...⟩ abbreviates the type of exception postcondition stack e₁ × (e₂ × (... × Unit)), and the notation estack⟨v₁, v₂, ...⟩ builds a value (v₁, v₂, ..., ()) of such a stack.

term ::= ...
    | Exception postcondition stack **type**: `EStack⟨ε₁ → l, ε₂ → l⟩` is `(ε₁ → l) × (ε₂ → l) × EStack⟨⟩`. EStack⟨term,*⟩
term ::= ...
    | Exception postcondition stack **value**: `estack⟨e₁, e₂⟩` is `(e₁, e₂, ())`. estack⟨term,*⟩

Specifications for programs that might throw exceptions come in two varieties. The total correctness interpretation ⦃P⦄ prog ⦃Q'⦄ asserts that, given P holds, then prog terminates normally and Q' holds for the result. The partial correctness interpretation ⦃P⦄ prog ⦃Q'; ⊤⦄ asserts that, given P holds, and if prog terminates normally then Q' holds for the result. A triple without an explicit exception postcondition carries the bottom assertion (⊥ : EPred) and thus has the total interpretation; between ⊥ and ⊤, the exception postcondition expresses a spectrum of correctness properties.

The partial order on predicate transformers is inherited pointwise from the assertion lattice: x ⊑ y when x.apply post epost ⊑ y.apply post epost for all post and epost. Every predicate transformer that a WP instance produces is monotone: if post ⊑ post' and epost ⊑ epost', then x.apply post epost ⊑ x.apply post' epost'.

17.2.3.1. Weakest Preconditions🔗

The weakest precondition semantics of a program type is provided by the WP type class. An instance WP Prog Value Pred EPred interprets programs of type Prog with results of type Value as monotone predicate transformers over the assertion type Pred and the exception postcondition type EPred. The type Prog determines Value, Pred and EPred as outParams. The function wp applies the interpretation: wp prog post epost is the weakest precondition under which the program prog establishes the postcondition post and the exception postcondition epost.

17.2.3.2. Monads That Preserve Weakest Preconditions🔗

Most of the built-in specification lemmas for vcgen rely on the presence of a WPMonad instance. A WP instance is provided for a particular type, but a monad is a polymorphic type. StateM Nat Unit and StateM Nat String are different types, but their weakest preconditions should be related. Instances of WPMonad assign a WP interpretation to each for every type that the monad can be applied to. It additionally contains evidence that this interpretation is sound for the monad's implementations of pure and bind. This means that to prove something about a Lean.Parser.Term.do : termdo block, it suffices to prove it about the chain of elements of the block. In other words, a WPMonad instance enables compositional reasoning about Lean.Parser.Term.do : termdo blocks.

17.2.4. Hoare Triples🔗

A Hoare triple (Hoare, 1969)Marginal noteC. A. R. Hoare (1969). “An Axiomatic Basis for Computer Programming”. 17.2.5. Specification Lemmas🔗

Specification lemmas are designated theorems that associate a Hoare triple with a program construct, such as bind, pure, a loop, or an application of a library function. A given program construct may have multiple specification lemmas that are applicable in different situations; they are tried in priority order until one can be instantiated.

The vcgen tactic decomposes a goal P ⊑ wp prog Q E by applying a specification lemma whose program matches prog, as the section on verification conditions describes. If no specification lemma applies to prog, then vcgen reports an error that names prog and the candidate lemmas. Specification lemmas make reasoning about programs modular: the specification lemma of a function f is proved once, and vcgen applies it at every call of f without unfolding the definition of f. In this respect, pure and bind are ordinary functions: the specification lemmas Spec.pure and Spec.bind hold in every monad with a WPMonad instance.

When applied to a theorem whose statement is a Hoare triple, the spec attribute registers the theorem as a specification lemma. These lemmas are used in order of priority.

The spec attribute may also be applied to definitions. On definitions, it indicates that the definition should be unfolded during verification condition generation.

A logical variable is a universally quantified variable of a specification lemma that does not occur in the program. Logical variables are used to relate the initial state to the final state and the return value.

An auto-framing specification is a specification lemma whose postcondition is a universally quantified variable, with a precondition that is stated in terms of that variable. When vcgen applies an auto-framing specification, unification instantiates the postcondition with the assertion that the rest of the program requires; this means that there's no need to prove that the postcondition entails the subsequent precondition. Every fact that the postcondition states about parts of the state that the program does not change is preserved without further proof. As an example, the specification lemma Spec.bind is auto-framing: its precondition is the weakest precondition of the first action with respect to the weakest precondition of the second.
